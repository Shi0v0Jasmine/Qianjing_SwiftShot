# 迁镜 ShotSwift：产品说明与首版需求

## 产品判断

首版服务一个具体任务：内容运营拿着喜欢的广告参考和零散产品素材，希望得到一支可以修改、检查和交付的短片初稿。迁镜提供的价值是把参考的表达顺序变成可编辑的创作结构，并让每个镜头的素材与缺口清楚可见。

人群定位是工作假设，尚未经过访谈验证。现有代码和演示视频证明了工作流的雏形，不能证明市场需求或实际提效幅度。

## 首要用户与 JTBD

- 用户：小品牌或小团队的内容运营，需要同时承担策划与基础剪辑。
- 触发：新品需要一支短视频，参考广告看起来有吸引力，但不知道怎样适配到自己的产品。
- 已有条件：参考、产品信息、一些素材；不一定有齐全的镜头。
- 当前替代方式：人工拆解参考、在文档中写分镜、回剪辑软件找素材，缺镜头时补拍或重新构思。
- 功能任务：组织信息、确定顺序、为分镜配素材、形成可编辑初稿。
- 情绪任务：减少面对空白画布的不确定感，知道自己可以控制哪些决定。
- 对外任务：能够向同事解释创作逻辑，并交出一个可播放的结果。

JTBD：当我需要制作产品短视频，手里有参考和零散素材时，帮助我把参考的叙事结构适配到自己的产品，得到可检查和修改的初稿，减少反复试错。

## UX 五层与设计决策

| 层次 | 本版决策 | 产品中的体现 |
| --- | --- | --- |
| 战略 | 让用户从参考走向可控初稿 | 单一案例、一条明确旅程 |
| 范围 | 优先完成五步闭环 | 输入、解析、分镜、补全、导出 |
| 结构 | 先理解，再编辑，再检查结果 | 左侧有序导航，可返回任一步 |
| 框架 | 中间看全局，右侧改局部 | 五镜卡片、时间线、单镜检查面板 |
| 表现 | 保留原品牌，降低阅读负担 | 深色工作台、玫红主操作、统一留白和中文文案 |

## KANO 假设与实施优先级

KANO 分类用于组织待验证需求，不用作已证实的用户偏好。分类与开发优先级不是同一件事。

| 需求 | KANO 假设 | 优先级 | 验收 |
| --- | --- | --- | --- |
| 明白下一步是什么 | 基本需求 | P0 | 每步有标题、解释与主操作 |
| 能修改字幕、时长和顺序 | 基本需求 | P0 | 修改出现在预览和导出中 |
| 素材缺口清楚可见 | 基本需求 | P0 | 文字与颜色共同提示；未补齐阻止导出 |
| 可播放与下载 | 基本需求 | P0 | 真实 MP4 文件可播放 |
| 较低的修改成本 | 绩效需求 | P0 | 右侧直接编辑，支持撤销和本机保存 |
| 理解结构迁移的理由 | 绩效需求 | P0 | 分析页解释结构作用和产品适配 |
| 一步得到补全建议 | 魅力需求候选 | P1 | 演示中可选预制候选，注明来源 |
| 实时模型生成 | 分类待研究 | 后续 | 本版不依赖实时模型通过演示验收 |

## 需求边界

本版采用虚构品牌“朝雾咖啡”：初始 5 镜、20 秒、1 处缺口。现场可改成 21 秒版本并导出。固定案例分析与 AI 预制图片均标明来源。视频由静态图片运镜与字幕合成，不声称已完成真实图生视频或自动质量评估。

演示项目里的 brief 与人群输入用于保存创作背景，不重新调用模型。自己的视频可进入保留的原版工作流，该链路仍需要原 API 配置，本版没有重做或重新验证它。

暂不扩展登录、计费、团队协作、批量投放、效果预测、移动端完整剪辑或实时 provider 稳定性工程。

## 成功标准

内部验收：从入口走完示例，至少修改一次字幕/时长、替换一次素材，补齐缺口，播放预览并下载有效 MP4；刷新保留项目；重置恢复初始状态。

后续定性验证：邀请 3–5 位接近目标人群的人，无提示完成任务，记录是否完成、卡在哪里、需要多少次帮助、能否解释结构迁移价值。这不是本版已完成的用户研究，也不用于推断市场规模。

## 待验证问题

1. 用户的主要困难发生在构思结构、找素材，还是调整成片？
2. 用户愿意保留多少人工控制，哪些决定希望系统代做？
3. 用户能否区分“结构迁移”与“套模板”？
4. 什么程度的初稿才值得他们继续编辑？
5. 缺镜头时，用户更愿意补拍、替换，还是 AI 生成？
