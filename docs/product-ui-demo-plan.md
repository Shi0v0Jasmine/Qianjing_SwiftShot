## 阶段 1：用户与产品定位（战略层）

工作假设：小品牌内容运营已有产品素材和喜欢的参考广告，希望更快得到可修改的广告初稿。该人群和需求尚未经过用户研究验证。

JTBD 初稿：当我需要制作产品短视频，手里有参考视频和零散素材时，我希望把参考的叙事结构适配到自己的产品，得到可以检查和调整的初稿，减少反复尝试。

行动：明确首要用户、触发情境、当前替代方案、核心困难和成功结果；梳理旧项目资料和参考视频。能接触用户时，做少量探索访谈，记录真实证据；不能接触时保留假设标签。

交付：一页产品说明、一个核心 JTBD、一个演示场景、待验证问题清单。

完成条件：能够明确回答“谁在什么情况下需要它，完成后获得什么价值”；不使用未经验证的节省时间或转化率承诺。

## 阶段 2：需求边界（范围层）

围绕同一案例组织需求。KANO 初始分类只是研究假设，不代表已完成问卷验证：

| 候选分类 | 功能示例 | 首版处理 |
| --- | --- | --- |
| 基本需求假设 | 导入案例、看懂结果、修改脚本、播放与下载、错误恢复 | 覆盖演示路径 |
| 绩效需求假设 | 素材匹配清晰度、修改成本、反馈速度 | 优先改善可感知部分 |
| 魅力需求假设 | 结构迁移可视化、缺失镜头补全前后对比 | 选择一个重点展示 |

KANO 分类需结合用户反馈验证；实施顺序还要结合核心任务、成本和依赖。首版不扩展账号体系、团队协作、批量生产或全面升级模型链路，除非发现它们阻塞核心场景。

交付：轻量 PRD、需求优先级、范围内外清单、验收条件。

## 阶段 3：原版 UI 审查与流程设计（结构层）

运行并查看原版页面，检查主操作、信息层级、术语、进度、返回与恢复路径。记录问题与用户影响；代码阅读不能替代视觉审查。

目标流程：打开示例 → 理解参考结构 → 输入新产品目标 → 审阅和修改分镜 → 匹配素材并解决缺口 → 预览和下载。

让每个分镜能回答：这一镜表达什么、用哪份素材、是否存在缺口、下一步能做什么。

交付：现状 UI 问题清单、用户流程图、页面与状态清单。

完成条件：每一页有明确主操作；用户知道当前步骤、结果意义及下一步。

## 阶段 4：线框与视觉方案（框架层、表现层）

先制作关键分镜工作台的线框及高保真方案供讨论，再扩展到导入、分析、素材缺口和导出页面。延续原项目有价值的品牌元素；根据实际审查决定保留与调整内容。

统一字体、字号、间距、颜色、按钮、卡片、状态提示和视频容器。覆盖加载、空白、失败、选中、禁用和完成状态；状态不仅靠颜色区分。桌面工作台优先，同时检查常见笔记本分辨率、文字对比和键盘焦点。

交付：关键页面设计、小型组件规范、中文界面文案。可以直接用 React 做可点击原型；Figma 是可选设计载体。

## 阶段 5：实现一条可靠演示路径

准备一个统一案例的参考视频、产品素材、结构数据、分镜、缺口和最终成片。先确认可用素材，再确定商品类别，避免不同页面使用不一致的案例。

演示模式使用固定数据和预生成媒体，明确标注演示来源；编辑、选择、跳转、预览、下载等交互真实可用。实时 AI 能力在配置可用时接入，不把预生成结果表述为现场即时生成。修改后若尚未重新合成，界面应说明当前预览仍为示例或上次生成版本。

技术工作以阻塞项为先：启动与依赖、媒体路径、关键请求、状态保存与重置、可播放文件和导出。保持现有后端契约，避免无关重构。

交付：可启动的本地 demo、完整示例素材、Windows 启动说明及演示模式说明。

验收：冷启动后可走完核心流程；关键操作有反馈；刷新恢复或清楚说明恢复方式；可重置；无断图和失效视频；下载产物可播放；实时/预制结果标识准确。

## 阶段 6：轻量可用性验证

邀请 3–5 位接近目标人群的体验者完成同一任务，作为定性可用性检查，不将小样本推断为市场结论。记录完成情况、犹豫位置、求助次数和对产品价值的理解；无法邀请用户时，先完成内部走查并明确其局限。

交付：问题记录及修复优先级。先修复阻塞任务和导致误解的问题，再优化装饰细节。

## 阶段 7：Remotion 展示视频

默认规格（可调整）：约 100 秒，1920×1080，16:9，30 fps，MP4；中文界面与字幕，无配音，默认无音乐。

推荐组合：已实现产品的真实操作录屏或截图 + Remotion 中文标题、重点标注、局部放大、结构映射动画和转场。视频内容与交付 demo 保持一致。加速或省略 AI 等待过程时注明；不得暗示未经测量的实际生成速度。

| 时间 | 画面与内容 | 需要讲清的价值 |
| --- | --- | --- |
| 0–8 秒 | 参考广告、零散素材和创作难题 | 用户为什么需要产品 |
| 8–18 秒 | 打开示例，展示目标产品与素材 | 开始任务需要什么 |
| 18–35 秒 | 展示参考的 Hook、卖点、证据和行动引导 | 如何理解叙事结构 |
| 35–57 秒 | 结构适配到新产品，展示一次脚本或时长修改 | 用户保留控制权 |
| 57–75 秒 | 展示素材匹配和一个缺失镜头的处理 | 如何从方案走向成片 |
| 75–93 秒 | 播放最终成片关键片段与下载操作 | 看得见的结果 |
| 93–100 秒 | 产品名与一句价值主张 | 观众应记住什么 |

旧视频可播放后，记录其时长、章节、字幕密度、镜头停留、转场和成片展示方式，再调整此草案，不假定目前已复刻参考风格。

制作顺序：参考拆解 → 中文字幕脚本 → 分镜表 → 10–15 秒风格样片 → 全片粗剪 → 检查与定稿。先检查短样片的可读性、节奏和渲染可行性，再投入完整渲染。

交付：最终 MP4、Remotion 项目源码、素材目录、字幕/脚本文件、渲染命令和封面图。

验收：无配音；静音观看也能理解；中文无缺字；字幕有阅读时间；关键界面可辨认；无黑帧或丢失媒体；文件时长/分辨率正确；完整观看最终导出文件并核对产品能力表述。

## 工具与用户所需提供的信息

- 无需先购买插件或连接额外 MCP。Remotion 可通过本地 Node.js/CLI 建立项目，依赖在视频阶段安装并锁定版本。官方安装文档：https://www.remotion.dev/docs/
- Remotion 项目建议独立放在 apps/demo-video，避免修改产品运行依赖。先做最小渲染测试，确认浏览器和渲染依赖。
- 原产品后端依赖 ffmpeg/ffprobe：先查是否存在可用安装，必要时再安装或配置 PATH；不要将它当作未经核验的 Remotion 通用安装前提。
- Figma 仅在需要可编辑设计稿时使用；无需为这一计划强制新增连接。
- 配音服务不需要。仅在选择背景音乐时准备有使用权的音频。
- 待提供：可播放的旧视频文件或其本地绝对路径；展示对象与截止时间（若有）；可用产品素材。视频无法访问不阻塞产品规划，但会阻塞准确参考其风格。

## 执行节奏

按三个可 review 的里程碑推进，不在缺少素材和界面审查时承诺固定工期：

1. 产品说明 + 原版 UI 审查 + 关键页方案。
2. 完整案例 + 可运行 demo + 可用性修复。
3. 视频脚本 + 风格样片 + 最终 MP4 与源码。

最先启动阶段 1–3。界面方向稳定后扩展实现；可录制的 demo 与统一素材准备好后完成视频制作。计划阶段不提前改动产品 UI。
